## Outcome

- Behind `?ui=next`, the owner picks a repository, sees only that repository's conversation and work, and sends a New request or a follow-up with the target always visible.
- Drafts survive navigation and reload, per repository and intent. Two rapid Enters send once. A retry resends the same payload and key; an edit gets a new key.
- Repo, work and task have addresses that survive reload and back/forward.
- The server refuses a chat message with no `repoId`.
- **Classic keeps working throughout and stays the default.** See "How classic keeps working".

## How classic keeps working

The `ui` flag is client-only (`apps/web/src/ui-flag.ts`, a localStorage value). It can hide the new shell, but it cannot gate a server rule. The flip to 400 therefore hits classic for everyone, and classic posts no `repoId` today (`api.ts` `sendChat`). So:

1. Classic learns to send `repoId` first. Requirements 17 to 20 land before the flip.
2. The flip is the **last commit** of this PR, alone, so it can be reverted without touching the rest.
3. `next` stays default-off. Do not add a Settings entry, palette entry or default change. Enabling it is the coordinator's step after verification (#15).
4. A tab still running the old bundle gets a 400. Classic restores the draft on failure (`Composer.tsx` `send`), so nothing is lost; reload fixes it.
5. Setup mode and the secret guard run before repo validation and stay unchanged, so Setup works with zero repositories.
6. Classic reads stay global: GET without `repoId` returns everything, as now.
