## Outcome

- A retry during planning admits one message and runs one planner turn.
- A crash after work is created resumes that same message on the same work item at boot, instead of being routed as conversation.
- An answered question always wakes the planner exactly once, and the HTTP answer returns without waiting for it.
- A launch that cannot run says so: the work is blocked with a reason and the effect row ends `failed`. It never settles as success.
- Shutdown is bounded and owns the planner's lifetime.

## Requirements

**Stable message identity (§12.1, §12.4, §20 Duplicate dispatch)**

1. `POST /api/chat/messages` mints `freshId('msg_')` per request (`server.ts:547`) and saves the idempotency key only after the planner returns (`:554-558`). A retry during planning finds no key and admits twice. Change: with a key, `messageId` is derived from it (`msg_` plus a truncated sha256 of the key), so it is stable. Without a key, keep `freshId`.
2. The key is stored in the first transaction, before the brain. Pass `idempotencyKey` through `onUserMessage` into `#saveMessage`. `#saveMessage` rebuilds the doc field by field, so it must carry `idempotencyKey` over, and any M1.2 `repoId`, on every later save. Remove the post-await patch at `server.ts:554-558`.
3. `onUserMessage` handles a receipt-less `prior` **before** `routeMessage`. Today the prior's own planning item is live, so routing returns `conversation`, and `#startNewWork`'s "resume" comment (`service.ts:436`) is unreachable. If `prior.workItemId` is set and the work is `planning`, resume `#startNewWork`. If that work is terminal, write the stopped receipt and do not call the brain.
4. In-process duplicates: keep a `Map<messageId, Promise<TurnOutcome>>`. A concurrent retry awaits the same promise, so one brain call runs. Clear it in `finally`. The route's early replay check (`server.ts:537`) must return the in-flight turn or the existing receipt-less doc as `routing: 'duplicate'`, never a new admission. Decide which by test; do not hold the HTTP request open on an unrelated turn.
5. `#replay` re-enqueues launches. Row deletion on success means this creates new rows; `launchAuthority` from `10` drops them. Confirm that with a test, and do not re-enqueue for work that is not `executing`.

**Durable wakes (§6, §17 relay, §26 Effects queue, Wake vs note)**

6. Wakes use the existing `relay` kind: no new effect kind and no contracts change. Add `enqueueWake({ causationId, reason, detail?, workItemId })` to the service, called only inside the caller's transaction. Key: `wake:<causationId>`. Payload carries the same fields.
7. The queue key alone does not dedupe. Success deletes the row, so a repeat after a drain makes a new row. So `onWake` takes the `causationId`, derives `messageId` from it (replacing `freshId('msg_wake_')`, `service.ts:312`), and returns the recorded outcome when that message already has `ackText`. A crash after the turn committed but before the row was deleted then re-runs as a no-op.
8. **Existing bug, source-read, not run:** `POST /api/questions/:id/answer` saves `status: 'answered'` (`server.ts:1467`), then calls `onQuestionAnswered`, which returns `not_open` because the doc is no longer open (`onQuestionAnswered`, `service.ts:358`). The planner is never woken over real HTTP. `planner.test.ts:137` misses this because it stubs the service. Fix: the service owns the answer. In one transaction it does the compare-and-set on `status`, records the answer, appends the event and calls `enqueueWake` with causation `question/<id>`. The route returns after that commit, so it no longer awaits a turn.
9. Run the answer through `redact` before the write, as the route does for chat (AGENTS non-negotiable 5). Base stores it raw. Keep the wake-less path for `deps.metaAgent` without the method, recording the answer as today.
10. Composition: `registerEffectHandlers` runs before the meta agent is built (`composition.ts:81` versus `:147`). Bind the `relay` handler to a late-set reference. With no meta agent, throw `Later`, so a wake waits for a configured slot instead of being lost. Relay is already ordered, one at a time (`effects-queue.ts:31`).

**Boot resume (§20 App crash, §26 Acknowledgement)**

11. At boot, after `reconcileRunningAttempts` and only with a meta agent: list messages with `routing: 'new_work'`, no `ackText`, and work in `planning`, and enqueue a relay `resume:<messageId>` per message. The handler calls `onUserMessage` with the stored text and the stored `repoId`, because M1.2 refuses a `prior` whose repo differs (`repo_mismatch`). It stays paused-safe, because it goes through the queue. Do not run the brain inline at boot.

**Truthful launch and effects (§17, CHANGE.md §Internal design 3)**

12. `launchHandler`'s non-fake path returns success with no launch (`launchHandler`, `composition.ts:366`). Change: after the `launchAuthority` check, block the work idempotently via `transition(..., 'block')` with `blockedReason: 'no_runner'` and an event, then throw. The row retries to `failed` with `last_error`. Do not use `Later`: a future runner would launch stale work. Skip the block if the work is already blocked. The attempt stays `queued` until the owner answers the open question on its state; that is the interim `20` also follows.
13. The remaining kinds are `async () => {}` (`composition.ts:343`). `grep` shows production enqueues only `launch` (`service.ts:764,924`), plus `relay` after this PR. Make `deliver`, `note`, `reply`, `external` and `probe` throw `unsupported effect: <kind>`, so nothing can settle as success. `fix/effects-double-run` adds a `composition.test.ts` case that enqueues `note` and expects the row drained. Move that test to `relay` and state it as an intended change.

**Lifetime (§20 Shutdown)**

14. `RealClaudeBrain` is built inline (`composition.ts:218`), so `close` cannot reach it. Hold the instance and call `close()` on shutdown. `RealClaudeBrain.close()` awaits its gate, so it can wait a full turn.
15. `close` (`composition.ts:232`) becomes bounded: stop timers, then race `drain` (or `settle` when paused) against 10 s (§20), then close the brain, then `db.close()`, then release the lock. It must not start a new planner turn during shutdown: pending `relay` rows stay for the next boot. See the open question. A late in-flight turn writing after `db.close()` must fail quietly, leaving its row `running` for `resumeRunning`.
16. **Scratch servers must not read real state.** `keystoreRoot` isn't passed by composition, so `PromptStore` (`server.ts:1767`) and the slot and models paths land on the real `~/.mec` even with a scratch data dir. Pass `keystoreRoot: opts.dataDir` to `buildServer`; a real install resolves to the same path. This comes first in the PR, because the real run below keeps the real `HOME`.

## Open questions

- **§17, launch "fails the attempt".** `ATTEMPT_STATES` has no failed state. Same question as `20-m2.1-real-specialist-slice.md` open question 2, which has the options and the recommendation (a terminal `failed` state, an owner call since it touches §10's table). The interim is the same in both: leave the attempt `queued`, block the work, let the row end `failed`.
- **§20 versus §17, shutdown.** §17 says shutdown "drains the queue"; §20 says shutdown "cancels turns gracefully, waits a bounded time" and then drains. Once `relay` is real, a drain can start a fresh paid planner turn on the way out. Recommend waiting for in-flight work only and leaving pending rows, since §17 also says "a restart resumes it".
- **§20 Pause, "messages keep being recorded".** A chat message during pause still runs a synchronous planner turn today, which spends quota, though its launches wait. Spec is silent on whether a turn may start. Recommend record-only during pause, with a `resume:<messageId>` relay, which this PR makes cheap. Implement only if the owner agrees; otherwise leave behaviour unchanged and record it.
- **§12.4 receipts.** The route still answers with the ack synchronously, so `received` and `ack` are not separate on the wire. Recommend leaving this to M2.2.
