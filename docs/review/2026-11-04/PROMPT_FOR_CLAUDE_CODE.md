# Prompts for the repository's Claude Code instance

Commit the review package first (`docs/review/2026-11-04/` and `docs/design/`), then run these as three separate sessions in this order. Each one ends with a PR, reviewed by the other person or a fresh instance before merge (branch protection on `main` is part of the first session).

## Session 1 — public repo hygiene and the one-command install (one day)

> Read `docs/review/2026-11-04/02_PUBLIC_REPO_REVIEW.md` and `01_ALIGNMENT_REVIEW.md` §5. Do every "Must fix" item and every "Should fix" item from §2 of the public-repo review, in that order, as one PR per numbered group where that keeps the PR small. Then implement §3.2 (the install path): ship the web UI inside the artifact, read the meta slot from the store, open the browser on first run, `mec --version` and `help`, the `install.sh` script, the `release.yml` workflow on `v*` tags, and the CI smoke that installs the tarball on clean `ubuntu-latest` and `macos-latest` runners. Replace the README's Quickstart with §3.3's text. Do not publish to npm until the owner confirms `DECISIONS.md` #2/#4 allow it; build the workflow so publishing is one commented line. Update `docs/STATUS.md` and `docs/known-limits.md` to agree. Tag `v0.1.0` when CI is green.

## Session 2 — model tiers, the real planner, prompts on disk, the setup agent (two weeks)

> Read `docs/review/2026-11-04/03_MODEL_TIERS_AND_PLANNER.md` end to end, then the spec's §6, §7, §16 and `docs/engines.md`. Implement the eight items T1–T8 of its §8 in order, one PR each. Rules: the capability table ships as `packages/prompts/defaults/models.yaml` exactly as §3 of the design, and the probe marks availability per slot before any tier is offered to the planner; `contracts-v0.1` is a reviewed change with a fixture update (the smoke recordings assert `resolved_model`); every prompt part ships as a default file under `packages/prompts/defaults/` and `META_PROTOCOL_TEXT` moves out of code; the nine platform tools are executed, not stubbed; the setup agent can only propose drafts that the person applies. Before T5, record one real `fast` and one real `balanced` attempt per engine on the real slots and keep them as fixtures. Acceptance is the paragraph at the end of §8; demonstrate it on `mec-sandbox` and record it in `docs/log/HANDSHAKES.md`.

## Session 3 — the workbench port (one week)

> Read `docs/review/2026-11-04/04_UI_DESIGN_SPEC.md` and open `docs/design/prototype/index.html` in a browser; look at every screenshot in `docs/design/screens/`. Replace `apps/web/src/styles.css` with the prototype's `tokens.css` + `workbench.css`, self-host Instrument Sans and Spline Sans Mono under `apps/web/public/fonts` (OFL; no runtime network), and port the components in the order of §7 of the spec, keeping the prototype's class names and the behaviours in `workbench.js`. Replace polling with the existing SSE feed. Add the API fields the spec's §7 lists (decision cards with what/why/facts/consequences/checks/findings; question cards; work-item and task detail; slot usage with `unknown`). Add the Playwright screenshot suite and the keyboard-only test from §10. The port is done when the §23 worked example renders like `screens/chat-light.png` with real data, in both themes, and axe reports no violations on any route.
