
## OpenCode 2.2.5 canary learnings (real serve API, 3 Nov 2026 — R2.2)

Recorded against slot glm-2 (z.ai GLM Coding Plan, key verified live against `https://api.z.ai/api/coding/paas/v4/models`, Bearer) and slot gem-1 (Google Gemini, `generativelanguage.googleapis.com/v1beta/models`, x-goog-api-key). Fixtures `smoke` (real, the adapter-driven OPENCODE-H1-OK turn) and `auth_expired` (real, garbage-key 401) are recordings; `rate_limit_rejected` and `permission_request` are synthetic in the real envelope (quota / spec-derived; see each meta.json).

**How opencode consumes keys (the launch recipe).** No `opencode auth login` needed — config-file providers carry API keys: an `opencode.json` in `$XDG_CONFIG_HOME/opencode/` (or `OPENCODE_CONFIG_DIR`) with `provider.<id>.options.apiKey: "{env:VAR}"` — `{env:}` substitution is resolved at launch, so the key rides the environment (keystore read → launch env) and NEVER enters a file opencode persists (verified: `debug config` prints `apiKey: "***"`). GLM: `npm: "@ai-sdk/openai-compatible"`, `baseURL: https://api.z.ai/api/coding/paas/v4` (the endpoint that bills Coding Plan quota), model `glm-4.7` (catalog: glm-4.5…glm-5.3-flashx-legal). Gemini: `npm: "@ai-sdk/google"`, model `gemini-2.5-flash` — same flow, verified with a real turn. `opencode auth list` lists only integration (OAuth) logins — a working key slot shows `[]`; the honest validity probe is the zero-token provider /models GET (slots probes, R2.6).

- **Isolation**: XDG_{DATA,CONFIG,STATE,CACHE}_HOME → the slot home; `OPENCODE_DISABLE_PROJECT_CONFIG=1`. CLI subcommands default to a SHARED background service on a fixed port (cross-slot hazard; one was already running) — always `--standalone` for CLI, `serve` per slot for the API.
- **`opencode serve --hostname 127.0.0.1 --port 0 --stdio`** prints exactly one stdout line `{"url":"http://127.0.0.1:<port>"}`; connect over HTTP with Basic auth user `opencode`, password from `OPENCODE_PASSWORD` (401 without, 200 with). **stdin EOF shuts the server down** (spawn with stdin piped open, never ignored). The full API surface + schemas: `GET /openapi.json` on the live server (zero-token ground truth, like codex `generate-ts`).
- **`POST /api/session`** takes `{location: {directory}, agent, model: {id, providerID}, permissions}`; the response is ENVELOPED `{data: {id}}`; the location directory MUST exist on disk (`LocationNotFoundError` otherwise); `session.create` without a model does NOT inherit the config-file default (pass `{id, providerID}` — the runtime owns the slot's provider profile, plan §5.7). Real agent ids: `build` (default), `plan` (read-only) — not `read-only`. `POST …/prompt {text}` always 200s (enqueue); failures arrive as events.
- **The real SSE stream** (`GET /api/event`): single `data: {"id","created","type","location","data":{…}}` lines — name top-level, payload nested under `data`; `: heartbeat` comments; no `event:` name lines. NO `session.idle`: the turn end is `session.execution.succeeded` / `.failed` — and the server keeps talking AFTER the verdict (a final cumulative `session.usage.updated`, `session.renamed`), so the adapter HOLDS the exit and flushes it at stream end (CONTRACTS §1 exit-last). Usage shape: `tokens: {input, output, reasoning, cache: {read, write}}` (not flat cache_read/write); the GLM Coding Plan reports `cost: 0` (subscription-style, never a number to charge); `session.usage.updated` fires more than once per turn, cumulative. Assistant text: `session.text.ended {text}`. Tools: `session.tool.input.started {id, name}` → `session.tool.called {id, input}` → `session.tool.success/failed {id, content, metadata.exit}` → one `tool_call`.
- **Errors** arrive as `session.step.failed` + `session.execution.failed` with `data.error = {type: "provider.auth", status: 401, message, response: {body: "<provider JSON string>"}}` — dot-namespaced types, the provider body stringified one level down (z.ai: `{"error":{"code":"1000","message":"身份验证失败。"}}`). Classification reads `type`/`status` plus the parsed body.
- **Permissions**: the runtime request is `Permission.Request {id: "per_…", action: "shell", resources: ["touch x"], save: ["touch *"], source: {type: "tool", id}}` — action `shell`, NOT `bash` (the config key is `bash`; the default `build` agent's ruleset starts `{action:"*",resource:"*",effect:"allow"}`, which swallows any appended ask — set `agent.build.permission.bash: "ask"` in the slot config to REPLACE it; a `permissions` ruleset on session.create alone does NOT ask). Reply: `POST /api/session/:id/permission/:perId/reply {decision: "once"|"always"|"reject"}` → **204 with an EMPTY body**; there is NO echo event — the adapter synthesises `permission_result`. **A reply POSTed from outside the SSE read loop (a `reader.read()` pending in flight) stalls the turn forever** — 204 lands, the pending list clears, execution never resumes; the identical reply between reads works, even 3 s late. The adapter therefore runs the whole round trip (bridge → reply → synthesised result) inside its SSE pump, between reads. Reproducible on both the free tier and glm-4.7.
- **Free tier**: opencode's built-in `opencode/glm-5.3-flash-free` models burn no Coding Plan quota — the permission-mechanism debugging ran there.

## Codex 0.148.0 canary learnings (real app-server, 3 Nov 2026)

Recorded against the logged-in `codex-1` slot (`CODEX_HOME=~/.mec/engines/codex/codex-1`, "Logged in using ChatGPT"); protocol cross-checked with `codex app-server generate-ts` (ships with the binary — the cheapest source of truth, zero quota). Fixtures: `smoke`, `permission_request`, `auth_expired` are real recordings; `rate_limit_rejected` stays synthetic.

- **Handshake**: `initialize {clientInfo:{name,title,version}, capabilities:{experimentalApi,requestAttestation}}` → `{userAgent, codexHome, platformFamily, platformOs}`; then the client NOTIFICATION `initialized` (no id) before anything else. `thread/start {cwd, sandbox, approvalPolicy}` → `{thread:{id,…}, model, …}`.
- **The plan's 0.166 description is wrong for turns on 0.148.0**: `turn/start` takes `{threadId, input:[{type:'text', text, text_elements:[]}]}` — not `{prompt}`; `turn/steer` needs `{threadId, input, expectedTurnId}` and `turn/interrupt` needs `{threadId, turnId}`. The turn id exists only in the `turn/started` notification (`params.turn.id`), so a steer/interrupt before events are drained is impossible — the adapter refuses with a clear error.
- **Approvals are server→client REQUESTS, not notifications**: the request id rides at the TOP level (`params.id` does not exist; the observed id was the number `0`). `item/commandExecution/requestApproval` params: `{threadId, turnId, itemId, startedAtMs, environmentId, reason, command, cwd, commandActions, proposedExecpolicyAmendment, availableDecisions}` — `command` is ONE shell-line string (`"/bin/zsh -lc 'touch approved.txt'"`), not argv. The answer is the JSON-RPC response `{"jsonrpc":"2.0","id":<same id and type>,"result":{"decision":"accept"}}`; `item/tool/requestUserInput` is answered `{"answers":{}}` — it has no decision vocabulary.
- **A read-only sandbox + `approvalPolicy: on-request` escalates writes** (the observed `touch`), while plain reads (`ls`) run in-sandbox without asking. `fileChange` approvals carry no paths — only `reason` and an optional `grantRoot`.
- **`turn/completed`** carries the whole turn: `params.turn.status` ∈ completed|interrupted|failed (+ `turn.error` when failed) — not a flat `status`.
- **`thread/tokenUsage/updated`** nests cumulative tokens under `params.tokenUsage.total` (`inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`); ChatGPT subscriptions report NO cost — `cost_usd` stays undefined, never 0.
- **`account/rateLimits/updated`** carries `params.rateLimits.{primary,secondary}` (300/10080 `windowDurationMins`; `resetsAt` unix seconds) — one event per window. Live slot readings at canary time: five_hour 0–1%, seven_day 16%, `planType: "team"`, credits enabled.
- **Auth expiry (empty CODEX_HOME) never ends the turn**: 401s arrive as `error` notifications `{error:{message:"Reconnecting… N/5", codexErrorInfo:{responseStreamDisconnected:{httpStatusCode:401}}, additionalDetails:"unexpected status 401 Unauthorized …"}, willRetry:true}` — the message alone says nothing about auth, classification must read `codexErrorInfo`/`additionalDetails` (401/unauthorized → auth). No `turn/completed` ever comes; the server retries forever, so the runtime must kill it and the exit is the CONTRACTS §1 crash-rule synthesis.
- **`mcpServer/startupStatus/updated` carries `error: null` in flight** — parsers must not mistake a null error field for an error notification.
- **The app-server never exits on its own** after a turn; consumers must stop draining at the `exit` event (or kill the process). Model on the slot: `gpt-5.6-sol`; `thread.cliVersion` is a reliable per-thread engine version.

## Stream input (Claude Code 2.1.318, probed against a local API stub, 5 Nov 2026)

No vendor call: a scratch home, a dummy key and `ANTHROPIC_BASE_URL` on a loopback stub. A real run on the slot is the verifier's.

- `system/init` waits for the first stdin line, then repeats at every turn.
- Each stdin line `{type:'user', message:{role:'user',content}, parent_tool_use_id:null, session_id, uuid}` gets `{type:'command_lifecycle', command_uuid:<uuid>, state}` lines: `queued` at once, `started`, then `completed` after its `result`.
- With `--replay-user-messages`, an `isReplay: true` user line with the same `uuid` arrives with the turn's response, not on receipt.
- A message written mid-turn gets its own turn and `result`. With no tool calls in the stub, joining a turn between tool calls is unobserved.
- After a `result` the process waits for stdin. EOF exits 0, and a message queued before EOF still runs.
- A follow-up's `content` is two text blocks: the person's words, then its input id and message id. Only the fake has read this shape on stdin so far; the probe used a plain string.

## Claude Code 2.1.318 specialist learnings (M2.1 builder runs, 5 November 2026)

Three real runs on a scratch repo through a linked slot, `model: claude-haiku-5-5`.

- **`--permission-prompt-tool` sends `{tool_name, input, tool_use_id}`**, not `tool_input`. The mec-tools schema still says `tool_input`, and the engine does not validate against it.
- **Asks need `--permission-mode default` on a linked slot.** Without it, no `mcp__mec__confirm` call arrived in run 1, even with `sandbox.autoAllowBashIfSandboxed: false`. With it, Bash and Write asks arrive. MEC reads nothing under `~/.claude`, so the setting that caused this was not identified.
- **`sandbox.autoAllowBashIfSandboxed`** defaults to true (the binary's own text says so), which skips the permission tool for a sandboxed command. MEC sets it to false.
- **`sandbox.filesystem.denyRead` and `allowWrite` are enforced on macOS:** `cat <dataDir>/mec.db` and a `touch` outside the worktree both gave `Operation not permitted`. A `git push` to a `file://` origin reached the remote side and failed there, `unable to create temporary object directory`.
- **`--disallowedTools 'Bash(git push:*)'`** refuses a command by prefix, before any ask. `git -C . push` is not that prefix.
- **`sandbox.credentials.files`** exists in the 2.1.318 binary, as part of a credential-masking feature with its own entry shape. It was not exercised, so `AttemptSettings` does not set it. `~/.claude` is in `denyRead` instead.
- **The sandbox grants a linked worktree's common git dir.** Seen in a real run: `git branch` wrote a ref into `<dataDir>/repos/*.git`, which `allowWrite` does not list. Read from the 2.1.318 binary's text, not run: a worktree whose common dir's name ends in `.git` has that dir added to the write list, with its `hooks`, `config`, `config.worktree` and `commondir` write-protected. `refs` and `objects` are not.
- **`sandbox.filesystem.denyWrite` wins over that grant, read from the binary, not run.** Each path becomes a `(deny file-write* (subpath …))` placed after the allows, in the same deny block as `hooks` and `config`, with unlink and create denied on the path and its parents, so `mv refs x` is covered too. MEC denies the whole shared clone for a specialist: `refs`, `packed-refs`, `objects`, the `worktrees/` admin directories and the clone's `HEAD`, which picks the next launch's base. A glob could not leave one attempt's admin directory writable, because deny beats allow, and a literal list misses attempts that start later. Seatbelt with that one rule, not the engine: `git status`, `diff`, `log` and `branch --list` work with the index unwritable; `add`, `commit`, `restore`, `stash`, `checkout -b` and `update-ref` fail at once and leave no lock.
- **The Read tool on a binary file** refuses by itself. A Read of a text file on the deny list was not exercised: the model declined it.

## Codex 0.148.0 through the attempt runner (M2.4 Part B, 5 November 2026)

Two real runs on a scratch repo, the linked `~/.codex` login, `gpt-5.6-luna` at low effort. `codex sandbox -P`, `initialize` and `thread/start` spend nothing, and answered most of this before any turn.

- **The sandbox can say all of what a worktree needs.** `default_permissions` selects a `[permissions.<id>]` profile, and `filesystem` takes `read`, `write` or `deny` per path, `:root` included. `deny` refuses reading too, so the deny list holds for the worker's shell as well as writes. The shared clone is `read`: `git status`, `diff` and `log` work, and refs, `packed-refs`, `objects`, the index and `update-ref` fail. Seen in `codex sandbox` with `touch` and `cat` and in both runs. Nothing about the clone's `.git` name matters on this engine.
- **`sandbox` on `thread/start` drops the profile.** With it, `activePermissionProfile` comes back `null` and `/tmp` is writable. Without it, the profile is active and `sandbox` reports `workspaceWrite` with empty `writableRoots`. The adapter refuses a launch whose thread has no profile.
- **An approval leaves the sandbox.** Under `workspace-write` and `on-request`, inside commands are not asked, so everything that reaches the client is a request to escape, and an allowed command runs unsandboxed (R2.1's canary saw the file appear). MEC refuses all of them. A command and a file change both asked and were declined, each as one native request with one answer, and `item/completed` then says `declined`.
- **`-c` tables merge, and each layer must parse alone.** `-c mcp_servers={mec=...}` leaves the user's servers running. `-c mcp_servers.x.enabled=false` is refused as `invalid transport`. `-c mcp_servers.x={command="true",enabled=false}` for stdio, or `{url=...,enabled=false}` for HTTP, stops it. `codex mcp list --json` names them and their transports. Only `mec` started once that was done, and `--disable apps,plugins` alone left four running.
- **A command the sandbox refuses leaves no item.** In both runs, commands that ended `Operation not permitted`, `git add` and `git commit` among them, produced no `item/started` or `item/completed`, while `git push` failing on the remote side did. The model saw their exit codes. The cause is not confirmed, and the journal therefore under-reports refusals on this engine.
- **`shell_environment_policy` keeps `MEC_TOOLS_TOKEN` from the shell.** `env | grep -c` printed 0 with the token in the app-server's environment. MEC names it in `exclude` as well as relying on the default filter.
- **The live catalogue is not the table.** `codex debug models` and `model/list` show `gpt-5.6-sol`, `-terra` and `-luna`. `packages/prompts/defaults/models.yaml` lists `gpt-6-*`, and the linked home's default is `gpt-6-astra` at `ultra`. The runs used a scratch `models.yaml`.
- **`model/list` answers per home (9 November 2026, zero tokens).** On an empty scratch home it is the binary's bundled list: `gpt-5.6-sol`, `-terra`, `-luna`, `gpt-5.5`, `gpt-5.2` and the hidden `gpt-5.4`, `gpt-5.4-mini` and `codex-auto-review` (fixture `codex/0.148.0/model_list`). On the signed-in ChatGPT `~/.codex` it listed `gpt-reserve`, `gpt-5.6-sol`, `-terra`, `-luna` and `codex-auto-review`, and no `gpt-6-*`. That sign-in refused `gpt-6-luna` with a 400 `model_not_found`. A launch now lists the slot's home before it resolves a model, and the shipped table leads with the `gpt-5.6` rows (`docs/changes/2026-11-09-codex-models/`). The call starts none of the home's MCP servers.
- **MCP tools** appear as `mcpToolCall` items, and `default_tools_approval_mode="approve"` ran `report` with no elicitation.
- **A linked home still adds** `~/.codex/AGENTS.md` and skills to the turn.
- **`thread/start` under a profile that can write the cwd trusts the repo cache.** It writes `[projects."<data>/repos"] trust_level = "trusted"` into `config.toml`, then loads project config, and a repository's own MCP server ran outside the sandbox. `-c projects={"<data>/repos"={trust_level="untrusted"}}` stops both; `project_root_markers=[]` does not.
- **Each command runs in its own process group,** as a child of the app-server, so signalling the server's group misses it. A background job from a finished command did not survive.
- **A `deny` refuses the path's own lstat (9 November 2026).** `"<data>/work"="deny"` with `"<data>/work/att_N"="write"` left the worktree writable but its parent unstattable, and Node realpaths every ancestor of a module, so `node --test` died `EPERM ... lstat '<data>/work'` (0.3.5, att_7). The sandboxed fs helper's `fs/canonicalize` failed the same way. The profile now leaves both parents readable and denies each sibling name by glob (`docs/changes/2026-11-09-codex-sandbox/`).
- **Globs in a profile only deny, and a glob beats any path.** `filesystem glob path ... only supports deny access`. `*` and `?` stop at `/`; `[!c]` negates; braces do not expand. `<dir>/*` refuses an entry but not what is under it, `<dir>/**` refuses what is under `<dir>` but not `<dir>`. `"<data>/work/**"="deny"` refused writes inside `"<data>/work/att_1"="write"`. A glob is a seatbelt regex, so it also refuses a directory made after the launch. Seen in `codex sandbox -P mec`, zero tokens.
- **A fileChange failed in a real run for a reason the stream does not say.** In att_7 (old profile) three fileChange items and in Codex run 9 (new profile) one came back failed; in run 10 (new profile) the same task's fileChange completed. The same patches, custom-tool and shell `apply_patch` forms, absolute and relative paths, under both profiles, through the real app-server and the real launch path with a mock Responses API (zero tokens), all completed. The item carries no error text, and `item/fileChange/outputDelta` is no longer emitted. The journal now keeps each fileChange's paths, kinds and status.
