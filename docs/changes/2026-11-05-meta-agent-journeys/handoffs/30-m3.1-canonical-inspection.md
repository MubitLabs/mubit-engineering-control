# M3.1: Canonical inspection and freshness

Read `00-README.md` first. This handoff is two PRs. Stage 1 is query-only and starts early. Stage 2 carries the trace access and waits for M2.

**Branch:** Stage 1 `feat/inspection-queries`. Stage 2 `feat/inspection-live`.
**Size:** Stage 1 M. Stage 2 L.
**Model:** Stage 1 a strong worker. Stage 2 the strongest available: it serves traces and artifacts.
**Start when:**
- Stage 1: `fix/release-cards` and `feat/repo-identity` are on `origin/main`.
- Stage 2: `feat/inspection-queries`, `feat/m2.1-specialist-slice`, `feat/m2.2-coordination` and `feat/m2.3-delivery` are on `origin/main`. M2.4 is not required.

**Can run alongside:**
- Stage 1: `31-m3.2-observable-work-ui.md` Stage A, `32-m3.3-setup-configuration.md`, `33-m3.4-accessibility-local-release.md` Stage A, and any M1 or M2 handoff.
- Stage 2: `31` Stages A and B, `32` (it adds to the `/api/status` handler, you to `buildHealthSnapshot`), `33` Stage A, and `23-m2.4-crash-capacity-recovery.md` both parts, which stay out of the `writeHealth` block in `composition.ts`.

**Blockers-only review:**
- Stage 1: not required. It serves only what existing routes already serve, redacted and bounded.
- Stage 2: required, by a different agent. It adds trace and artifact access, and it tightens who may read them.

**Real-engine runs:** none, in both stages. Evidence comes from seeded records, the fake engine and what M2's own proofs leave behind.

## Outcome

Stage 1: a client can read any repository's work, tasks, open decisions and search results through bounded pages. Each row has a title, a repository, the §10 stage, a reason and a next action. What is not yet recorded is labelled, never shown as zero.

Stage 2: a client can go from a task to its attempts, exact-head checks, diff, redacted activity and artifacts. It can stay current over one bounded connection and tell a dead server from a quiet one. A clean process exit is never counted as delivered.

## Requirements

### Stage 1: query-only

1. **Keyset reads, no migration.** New `packages/store/src/inspection.ts`: `class InspectionReads`, built from `SqliteStore.db`. Page docs with `WHERE kind = ? AND rowid > ? ORDER BY rowid LIMIT ?`. Page events with `WHERE stream = ? AND seq > ? ORDER BY seq LIMIT ?`.
   - The first form needs no new index. `EXPLAIN QUERY PLAN` on the current schema gave `SEARCH docs USING INDEX doc_kind_idx (kind=? AND rowid>?)` in both directions (scout run on a scratch in-memory copy). Re-check it in a test.
   - The rowid is safe as a keyset: the upsert in `store.ts` (`DocsRepository`) updates in place, and no code runs `VACUUM`.
   - Do not add to the `Store` interface in `packages/contracts`. No contracts change is allowed here.
2. **Migration trip wire.** Equality on a JSON field scans the kind: 17 to 20 ms over 50,000 task rows of about 700 bytes in that scout run (Python sqlite3, synthetic). The plan sets no budget, so this handoff proposes one: if any page read exceeds 100 ms at 50,000 docs of its kind on a Node run with real better-sqlite3, **stop and report the numbers**. Adding an index or generated column needs a SQL migration, which is not authorized. Never work around this with a table, a persisted projection or a new database file.
3. **Bounds (§17, CHANGE.md "Bounded live observation").** Default limit 50, maximum 100, and each response at most 1 MiB of JSON. A byte cap ends the page early with a valid `nextCursor`. A malformed cursor or limit answers 400 before any query. The cursor is opaque base64url of `{v:1,r:<rowid>}`.
4. **One stage, computed from facts (§10).** Change `packages/domain/src/stages.ts` to the spec's table and order: person/decision, person/login, person/review, person/blocked, held, waiting/quota, working/queued, idle, working. Use the spec's labels.
   - The code today puts `held` first, and the spec puts a person stage before it. The spec decides. `stages.test.ts` pins the old order, so changing it is an **intended behaviour change**: say so in the record.
   - `stageOf` has no production caller today (only `packages/domain/test` and the index export), so nothing else moves.
   - The spec says "open" items only. An ended item shows its outcome (§18.3): merged, closed, stopped by you, dropped.
   - A fact that is not recorded yet cannot match its row, and the DTO's `coverage` says so.
5. **Read routes, additive.** Add `GET` routes under `/api/inspect/`. Leave `/api/work` and the other existing routes unchanged: the classic shell reads them until `33` removes it.
   - `snapshot?repoId=`: repositories, needs count, and the cursor vector for the streams the snapshot covers, all read in one synchronous call so they agree.
   - `work?repoId=&cursor=&limit=`, `work/:id`, `tasks/:id`.
   - `needs?repoId=&recent=1`: open questions and pending cards, plus recently settled and expired ones.
   - `search?q=&repoId=`: messages by text or id, work by title, tasks by name, and references such as `#12`, a GitHub URL or a SHA where a stored field holds them (§18). Attempt ids join in Stage 2. Bounded, labelled per result kind.
6. **The wire shape below is the contract.** `31` builds against it before this ships. If you must change a field, tell the coordinator before you commit.
7. **Title.** Work docs have no title at `a102313` (`service.ts`, `server.ts` `POST /api/chat/messages`). Serve `title` if a doc has one, otherwise the first line of the origin message, redacted and cut to 80 characters, otherwise `null`. No model call.
8. **Legacy (CHANGE.md "Compatibility").** A row with no `repoId` serves `repoId: null`, `repoLabel: null`, `readOnly: true`. Never infer a repository from a path, title or branch.
9. **Redact at the boundary (§17, §22).** Every string in every response passes through `redact(text, [], [])` from `@mec/slots`, in the desktop DTO builder. The store cannot import slots. This is a second line, not a fix: only `POST /api/chat/messages` (`server.ts`) and the release cards (on `fix/release-cards`) redact before write, and `packages/meta/src` has no `redact` call at all. So planner-written task text reaches the store unfiltered. Report that gap in your finish report; a write-side fix is not in this PR.
10. **Join only what is proven.** `ConfirmationRecord` has no `workItemId`, and release cards store `payload {repo, branch, ...}`. Join a card to work only through a stored field or `mandateId`. Otherwise serve `workItemId: null` and the payload's repo as a label. Never join on branch name. `awaitingConfirmation` is true only for a proven join.
11. **Honest counts (§18).** `needsCount` equals the length of the `needs` list it links to, computed by the same function.
12. **Docs.** Add the routes to `docs/reference.md`.

### The wire shape (Stage 1 fixes these names; Stage 2 fills the empty parts)

```ts
type Page<T> = { items: T[]; nextCursor: string | null; observedAt: string }

/** false means not recorded yet, which is different from none. */
type Coverage = { reports: boolean; checks: boolean; diff: boolean; activity: boolean; usage: boolean; delivery: boolean }

type Stage = { key: string; label: string; waitingOn: 'person' | 'system' | 'none' }

type WorkRow = {
  id: string; title: string | null; repoId: string | null; repoLabel: string | null; readOnly: boolean
  state: string; stage: Stage; reason: string | null; nextAction: string | null
  taskCounts: { total: number; byStatus: Record<string, number> }
  lastActivityAt: string | null; updatedAt: string
}

type TaskRow = {
  id: string; localKey: string | null; title: string; role: string | null; status: string
  dependsOn: string[]; planRevision: number | null; attemptCount: number
}

type WorkDetail = WorkRow & {
  originMessageId: string | null
  goal: string | null
  hold: { since: string; reason: string | null } | null
  planRevision: number | null
  tasks: TaskRow[]
  /** Parent and child attempts. Empty until M2 records them; never inferred from dependencies. */
  delegation: { parentAttemptId: string; childAttemptId: string }[]
  delivery: DeliveryView
  coverage: Coverage
  cursors: Record<string, number>
}

type AttemptView = {
  id: string; generation: number; state: string; role: string | null
  requested: { tier: string | null; model: string | null }
  actual: { model: string | null; engine: string | null; slotLabel: string | null } | null
  baseSha: string | null; headSha: string | null
  processOutcome: string | 'unknown'
  lastActivityAt: string | null
}

type CheckView = { name: string; state: 'passed' | 'failed' | 'not-run'; headSha: string | null; detail: string | null; artifactRef: string | null }

type TaskDetail = TaskRow & {
  workItemId: string; repoId: string | null; objective: string
  attempts: AttemptView[]
  /** Only for the exact head named; never inherited from another scope. */
  checks: { headSha: string | null; results: CheckView[] }
  diff: { headSha: string | null; summary: string | null; files: { path: string; added: number; removed: number }[] }
  usage: { reportedUsd: number | null; missingAttempts: number; mode: 'api' | 'subscription' | 'unknown' }
  coverage: Coverage
}

type DeliveryView = {
  stage: 'none' | 'local-complete' | 'awaiting-push' | 'awaiting-pr' | 'pr-open' | 'pr-ready' | 'merged'
  branch: string | null; headSha: string | null; prNumber: number | null; prUrl: string | null
}

type NeedItem =
  | { kind: 'question'; id: string; repoId: string | null; repoLabel: string | null; workItemId: string | null
      question: string; options: string[]; status: 'open' | 'answered' | 'expired'; askedAt: string | null; answer: string | null }
  | { kind: 'card'; id: string; repoId: string | null; repoLabel: string | null; workItemId: string | null
      cls: string; status: 'pending' | 'approved' | 'denied' | 'expired' | 'stale'; expiresAt: string; detailPath: string }

type SearchHit = { kind: 'message' | 'work' | 'task' | 'attempt' | 'reference'; id: string; title: string; repoLabel: string | null; workItemId: string | null }

/** Stage 2. One page item of `attempts/:id/activity`. `31` Stage C binds it. */
type ActivityItem = { seq: number; type: string; at: string; summary: string; detail: string | null }
```

Stage 1 serves `attempts`, `checks`, `diff`, `usage` and `delivery` from what is stored, with `coverage` false for anything not yet recorded.

### Stage 2: trace access and freshness

1. **Read gate, enforced on the routes (§22).** The hook at `server.ts:428-450` blocks a bad `Origin` and requires `x-mec-client` only on mutating methods. A same-origin GET sends no `Origin`, and `Host` is not checked, so a DNS-rebound page can read a GET response. For all `/api/inspect/*` routes add a route-level check: the `Host` hostname must be loopback, and `x-mec-client: 1` is required on any browser-shaped request. The web client already sends the header (`api.ts` `request`). Apply the `Host` check to `/api/events` too: `EventSource` can't set a header, but its `Host` is loopback. Do not change the hook itself.
2. **Evidence.** Fill `attempts`, `checks`, `diff`, `delegation` and `delivery` from the records M2.1 to M2.3 actually wrote. Read the merged shapes. A field with no record stays empty with `coverage` false; report it, and don't invent a record. Requested and actual model stay separate (CHANGE.md design item 7).
3. **Activity pages.** `GET /api/inspect/attempts/:id/activity?cursor=&limit=`. Allow-list contract event types: `message`, `tool_call`, `permission_request`, `permission_result`, `usage`, `rate_limit`, `report`, `error`, `exit`, `session_started` (`packages/contracts/src/events.ts`). Drop anything else. There is no reasoning event type in the contract; don't add one. `tool_call` is a completion, so "currently running" is never derived from it.
4. **Artifacts.** `GET /api/inspect/artifacts?attemptId=&ref=`. Resolve `ref` only under the attempt's allow-listed root. Use `realpath` and refuse `..`, absolute paths and symlink escapes. At most 1 MiB per page. Served as `text/plain` with `x-content-type-options: nosniff`, redacted on read. Binary files return metadata only. Executable markup is never served.
5. **Bounded events.** Change the `/api/events` route only:
   - Cap each flush per stream, and stop writing when `raw.write` returns false until `drain`.
   - Add `?compact=1`: frames carry `{stream, seq, type, at}` and no body.
   - Past a backlog cap, send one `event: reset` frame with a reason and end the response, so the client takes a fresh snapshot.
   - Redact bodies in the non-compact form.
   - Today: `flush` reads every tail unbounded. The merged form from `fda9b4d` is already one connection, so keep it. Native `EventSource` reconnects with the original `after` values and the server ignores `Last-Event-ID`, so each reconnect replays history. Keep the comma-aligned query as the resume mechanism; `31` closes and reopens with its own cursors.
6. **Liveness (§21.2, research-observability).** `health.json` gains `instanceId`, `pid` and `heartbeatAt`. Remove the identical-text skip in `writeHealth` (`composition.ts`, around line 127), so the file really is rewritten each tick. `statusFromSnapshot` treats a stale or missing heartbeat as `not answering`, exit 1. The spec gives no threshold, so this handoff proposes 10 s, five 2 s ticks. Parsing stays tolerant of older files. `buildHealthSnapshot` hardcodes `answering: true` (`server.ts:334`): add `observedAt` there, keep the `paused` state `10` wires in, and the server's own answer never claims more than it knows.
7. **Accounting (§19).** In `packages/scorecards`: `costUsd` and `spend` come from one mode-aware calculation, and `project.ts:157-159` no longer takes the last usage event. Add coverage, so a known subtotal is never labelled a total. Separate process, validation and delivery outcomes. `aggregate.ts:45-46` and `tiers.ts:129` count `completed` as success: relabel to process completion or base them on validation evidence. Missing data is `unknown`, never 0. Derive on demand per work item. No stored projection in this PR: it would need a table.
8. **One stage everywhere.** `packages/meta/src/context.ts` around line 526 reads `doc.stage ?? doc.state`. Replace that one expression with the projector, so chat and Work agree (§10). No other edit there.
9. **Search** gains attempt ids.
10. **Keep the redaction, repo and read-only rules from Stage 1 on every new route.**

## Verifier instructions

A separate agent, on the built product. Use a scratch `MEC_DATA_DIR` and a scratch `HOME`: `pnpm install --frozen-lockfile && pnpm build:desktop && pnpm --dir apps/web build`, then `MEC_NO_OPEN=1 MEC_FAKE_ENGINE=1 node apps/desktop/bin/mec.js`. Without `dist` the launcher's source fallback fails. The port is ephemeral: read it from the "mec server listening on" line.

Stage 1:
1. Register two scratch repositories. Send one request in each, on plans that reuse `task_1`.
2. Page `work` for each repo and for all; no row leaks across a repo filter.
3. Restart the server and repeat; the links hold.
4. Seed 50,000 task docs into a scratch database only, measure list and detail read times, and report them against the 100 ms trip wire.
5. Compare `snapshot` counts with direct SQLite reads of the scratch database.

Stage 2:
1. Send requests with a forged `Host` and with browser headers but no client header; both are refused.
2. Disconnect a real SSE client while facts change, reconnect from its cursors, and compare against SQLite: no gap, no duplicate.
3. `kill -9` the server. `mec status` must stop saying healthy within 10 s. `mec status` reads `$HOME/.mec` (`cliMain` in `mec.ts`), so for this step set `MEC_DATA_DIR` to `$HOME/.mec` under the scratch `HOME`.
4. On a record with a clean exit and a failed check, no route may say delivered.
5. Open every string route with a seeded key-shaped value; none returns it.

## Open questions

1. **§17, indexes.** The spec says records have generated columns and indexes over active sets. The schema has only `doc_kind_idx` (`migrations.ts`). Recommendation: leave it unless the trip wire fires, then ask the owner for a migration.
2. **§19, projection.** The spec says a projection builds outcome records, and CHANGE.md design item 7 proposes an incremental view with watermarks. That needs a table. Recommendation: derive on demand in this PR and keep the stored version for a separately approved migration.
3. **§18, §19, transcript depth.** Research marks full redacted tool input and output on demand as recommended, not owner-confirmed. Recommendation: serve it redacted, behind the read gate.
4. **§20, retention of traces.** Traces can hold source code, and no cleanup runs today. Recommendation: no deletion in this PR; the owner decides later.
5. **§10, stage for `planning` with no tasks.** The table's last row makes it Working. Recommendation: keep it; `reason` says planning.
