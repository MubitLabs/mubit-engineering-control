## Outcome

Local checks on the exact head decide acceptance, not an engine exit. Accepted tasks merge into one integration worktree, and combined checks run on the exact merge SHA. When every required task is in, MEC reports a useful local result and opens a push card. An approved push leads to a PR card, and an approved PR plus observed checks yields a tested PR ready for review. Merge stays a separate decision. A declined card keeps the local result.

## Requirements

1. **Check profiles (§14, §15).** Load from the repo doc pinned at admission (M1.2's profile hash). Replace `knownChecks: [MANUAL_REVIEW_CHECK]` (`service.ts:573`) and pass real names to `PlannerTools` (`#buildTools`). An unknown check is refused by name. `manual-review` stays only as the "no checks registered" marker, which can never pass by itself.
2. **Exact-SHA verdicts (§15).** Every verdict binds its SHA. A head that moves invalidates it, and a stale green is never reused. Keep *failed* (ran, non-zero) separate from *error* (could not start, timed out): `CheckOutcome.status` already does.
3. **Acceptance.** Replace 21's interim rule with a pure reducer in `packages/domain/src/acceptance.ts`. Input: attempt state, verdicts on the reported head, findings, policy. A `ready` report without passing checks on its `head_sha` isn't acceptance (§10, §15). UI evidence (§15) applies only where the repo requires it; repo docs have no such field yet, so treat it as not required and say so.
4. **Review policy (#13, §15).** No reviewer task is added for routine work. A task classified sensitive gets one read-only reviewer attempt on a different session; findings bind the SHA. Add `reviewRoundsPerTask: 3` to `Caps` (§11; `caps.ts` has no such field). `repairAttemptsPerTask` exists. The round count travels in reports. See the open question on classification.
5. **Bounded repair (§11, §15).** `checks_failed` or a finding produces a repair attempt on the same worktree with exact evidence: failing check, log tail, SHA. At the cap the task blocks with what remains. Never a loop. `scorecards` and the UI are not touched here.
6. **Integration controller (§14).** New `packages/integration/src/controller.ts` with injected git and check functions, driven by `nextIntegrationStep`. One integration worktree per work item, from the pinned base, branch `mec/<work-item8>/integration`.
   - One task per run: `mergeIntoIntegration`, then checks on `mergeSha`.
   - Conflict: repair in the mid-merge worktree via `prepareMidMergeRepair` and `completeMidMerge`, which proves two parents.
   - Failing combined checks: repair with reason `checks_failed`.
   - `integration` dependents start from the integration commit: update 20's pin hook.
   - The queue's `done` covers "nothing was accepted" (`queue.ts` header). It's never whole-work success.
7. **Work state.** Drive `executing → reviewing → integrating` through `WORK_ITEM_MACHINE`. Nothing moves work to `done` in production today.
8. **Result reducer.** Pure, in `packages/domain/src/work-result.ts`. A work item is locally complete only when every required task is `integrated` or explicitly excluded with a reason, combined checks passed on the current integration head, and findings are dispositioned (§15 definition of done). An accepted subset is not success. `report_result` persists an event only (`#persistExtras`). The meta agent speaks from the reducer's output and can't invent it.
9. **Duplicate check (§14).** Call `yieldCheck` before opening a push card. A human PR containing the change gives `dropped` and opens nothing. It hardcodes `main...branch`; pass the pinned default branch.
10. **Push source seam.** `pushTarget` takes `gitDir` from the registered path and `localHead` reads `refs/heads/<branch>` there (`release.ts:794,815`). The integration branch lives in the bare cache, so a card would answer `head_unreadable`. Add a resolver in `ReleaseDeps`: push from the cache `gitDir`, take the GitHub slug from the registered clone's `origin`. A URL-registered repo answers `repo_not_local` today; with the cache it can push, but its slug comes from the URL. Keep refusing the default branch. Keep caller-free paths: no caller ever supplies a directory.
11. **Result path.** Deterministic controller, no agent tool:
    - Local result recorded, then `openPushCard(repoId, branch, headSha)`. Nothing is approved here.
    - On an approved, successful push, `createPrBehindCard` with `buildPrBody` (§14: requirements, SHAs, check evidence, findings, slots). No bot run ids.
    - Add one `onCardSettled` hook to `ReleaseDeps`, called by `resolveReleaseCard`, so continuation doesn't depend on who answered. Each effect keeps its own card. No card is pre-approved or skipped (#11, §13 invariant 1).
    - After `pr_create`, drive `prTransition`. Read required checks with the gate's existing reader.
12. **Tested PR ready (#12).** Requires an open PR on the integration head, local combined checks on that SHA, and required checks passed as read from GitHub. Pending approval isn't delivered. `no_required_checks` is the open question below. Never announce from an API success: observe state.
13. **Decline and failure.** A denied or expired card leaves the local result and shows the PR target pending. No retry without a new card. A failed push or PR is visible with its stderr, and approval is spent (`resolvePush`).
14. **Merge.** Never opened automatically by this flow. `merged` only from GitHub state (§14). The card and route exist.
15. **Stale.** Target movement re-runs required checks (`target_moved`). A new commit on the integration branch moves the PR back to not ready.

No contracts change and no SQL migration expected. Stop if either seems needed.

## Open questions

1. **§10 and #12: when is a work item `done`?** `integrating → done` exists, but default delivery stops before merge. Recommend staying `integrating` with stage Ready for review until GitHub confirms merge or the owner closes it. Consequence: open PRs keep work live, so M1.3's New request path must stay available beside it.
2. **`no_required_checks` (release-cards Risks).** gh gives the same answer for a repo with no required checks and for one where checks haven't started, and the gate fails closed. Recommend: PR ready on local combined checks with the limit stated; merge card stays held. A repo without required checks needs the owner's decision before use.
3. **§15 and #13: what is sensitive?** The standing cases are secrets, sign-in, permissions, money, stored-data deletion or migration, and public posts. Nothing classifies a task as one. Recommend a planner-set flag plus a deterministic path list per repo, and only the flag until the repo field exists. Don't invent a classifier.
4. **§14: which default branch?** Repo docs don't store one. Recommend the one read at pin time (20's open question 1).
5. **§14: repair as a new task or a new attempt?** §14 says repair task; §11 caps repair attempts per task. Recommend a repair task for integration conflicts, a new attempt for a task's own failed checks, and the same counter.
