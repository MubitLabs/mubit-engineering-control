# M0 — Foundation

**Backlog ticket:** 01 (monorepo, contracts, migrations, CI).

## What it does

Sets up the TypeScript monorepo and the two things every later milestone builds on:

1. **The durable event log** (`apps/control/migrations/0001_event_log.sql`). Every state change
   writes an `events` row in the same transaction. Events belong to a *stream*
   (`project:<id>` or `fleet`) with a gap-free `seq`. Appending locks the stream row, so a client
   that resumes from `seq = 41` can never miss a row that commits late.
2. **The transactional outbox** (same file). Work that must leave the database (dispatching to a
   runner, notifications) is written as an `outbox` row in the same transaction as the decision
   that caused it, then delivered by a dispatcher (M4/M5).

## How to read it

| Path | Purpose |
| --- | --- |
| `apps/control/src/db/migrate.ts` | Migration runner: numbered SQL files, one transaction, advisory lock, checksum guard. |
| `apps/control/migrations/` | Plain SQL, one file per milestone that needs schema. |
| `packages/contracts/src/runner-protocol.ts` | The runner event envelope from PDF §25 as a Zod schema. |
| `apps/control/test/helpers/db.ts` | Creates a throwaway database per test file. |

Tooling: pnpm workspace, TypeScript strict (`tsconfig.base.json`), Biome for lint + format,
Vitest for tests, `docker-compose.yml` for a local Postgres 16 on port 5434.

## How to demo

```bash
pnpm install
pnpm db:up          # local Postgres 16 on 127.0.0.1:5434
pnpm check          # typecheck + biome + vitest (unit + Postgres integration)
DATABASE_URL=postgres://mec:mec@127.0.0.1:5434/mec pnpm db:migrate
```

The migration tests prove: a fresh database migrates, a second run is a no-op, two concurrent runs
apply each file once, an edited migration is refused, and a failing batch rolls back entirely.
