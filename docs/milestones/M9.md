# M9 — Review, integration and the pull request

**Backlog tickets:** 18 (independent review and result acceptance), 19 (integration lease,
dependency order, repair tasks), 20 (PR creation, CI and review state — with a token instead of the
GitHub App for now).

## What it does

- **Review is its own decision.** When an attempt succeeds (checks passed on its head SHA) the task
  waits for review and a `result` approval is opened for the delivery owner, bound to that exact
  SHA. *Accept* records the accepted commit; *Send back* records the reviewer's notes and the next
  attempt is a **repair** that starts from the previous head, is reviewed against the original
  base, and gets the notes in its brief. Failed checks do the same with the exact failures (check,
  status, log tail). Repairs count against the task's attempt budget; when it is spent the task
  waits for a person.
- **Integration queue.** For every executing delivery, under a single integration lease, the
  integrator takes the next accepted task whose prerequisites are integrated and starts an
  integration run on the runner that holds the commit: a detached worktree at the current
  integration commit, `git merge --no-ff` of the accepted SHA, then the repository's integration
  checks on the **exact resulting SHA**, then push of `mec/<delivery>/integration`. One task per run
  keeps the evidence and blame clear. A dependent task (`basePolicy: integration`) becomes ready
  only after its prerequisite is integrated and starts from that integration commit; an interface
  dependent (`contract`) starts once the prerequisite is accepted.
- **Conflicts and failing combined checks** send the task back with a repair context. For a
  conflict the repair worktree starts at the integration commit with the task's earlier change
  **mid-merge**, so the agent resolves both sides and the merge completes with two parents. Nothing
  is silently discarded and the delivery does not restart.
- **The pull request.** When every task is integrated and the integration commit is on the remote,
  control opens the PR through the GitHub REST API (body: requirements with covering tasks, tasks
  with accepted SHAs, checks on the integration SHA, decisions) and polls it. The delivery becomes
  `merged` only when GitHub reports the PR merged; a closed PR returns it to `integrating`.

## How to read it

| Path | Purpose |
| --- | --- |
| `apps/control/src/features/integration/review.ts` | Result approval binding and accept / send back |
| `apps/control/src/features/integration/integrator.ts` | Integration queue, PR creation, PR polling, PR body |
| `apps/control/src/features/integration/outcomes.ts` | Integrated / conflict / failed-check projections |
| `apps/control/src/features/integration/github.ts` | GitHub REST client |
| `apps/control/src/features/attempts/service.ts` (`startPayload`, `requestReview`) | Bases for dependents, repairs and integration |
| `apps/runner/src/runner.ts` (`runIntegration`), `apps/runner/src/workspace.ts` (`integrate`) | Merge, checks, push on the runner |
| `packages/git/src/worktrees.ts` (`mergeCommit`, `beginMerge`) | Merge primitives |

## How to demo

`pnpm vitest run apps/control/test/integration-e2e.test.ts` — accepting records the exact commit;
send-back repair continues from the previous head; failed checks hand over the failures; two tasks
integrate one at a time with checks on each exact merge SHA, the integration branch is pushed, the
PR is opened with a full body, and the delivery is marked merged only after the (fake) GitHub says
so; a dependent starts from the integration commit; a conflict is repaired with both changes and
integrates.

Live (needs a fine-grained token for `MubitLabs/mec-sandbox`: `GITHUB_TOKEN` in
`/etc/mec/control.env` and `MEC_GIT_TOKEN` in `~max/.config/mec/runner.env`): approve a plan, accept
each result in the inbox, and the integration panel on the delivery page shows each run and then the
PR link.
