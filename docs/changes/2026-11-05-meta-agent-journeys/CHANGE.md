## Outcome and agreed product decisions

The owner asks one meta agent for a coding outcome in a repository. The meta agent plans, assigns specialists, monitors, repairs and delivers. The owner can understand every task and inspect its activity/evidence without manually managing specialist sessions.

The owner confirmed four product choices:

1. **A separate meta conversation and work history per repository.**
2. **Autonomous planning and local execution under policy; ask before push, PR creation or merge.**
3. **Default delivery is a tested PR ready for review.** Merge is a separate decision.
4. **Routine builder failing-then-passing checks and meaningful mutants suffice; one blockers-only review for the standing sensitive cases.** Preserve required human repository reviews. No unnecessary reviews.

These decisions approve direction, not execution of this session. The user asked for the whole plan before building and subsequently requested a **full visual and UX overhaul with Apple-like finesse**. ## Internal design: focused boundaries around existing helpers

Keep SQLite single-writer core, package boundaries, adapters, per-attempt journals, deterministic domain logic and effects/confirmation machinery. No new framework, telemetry service, database, ORM or broad dependency upgrade.

1. **Admission identity.** Repo → per-repo conversation → work/mandate → versioned plan → canonical tasks/dependencies → attempts. New admission pins repo/base/profile/policy/bundle revisions. Allocate global IDs and rewrite planner-local dependency keys atomically; preserve display keys. Validate collection kind and association at every command/launch. A view switch never retargets work.
2. **Durable commands/authority.** Narrow command handlers for admit/follow-up/answer/hold/lift/stop/pause/resume. Persist command identity before awaiting engines. Deduplicate wakes by causation, resume incomplete admission before new routing, fence commit and tool calls by current mandate/generation. Follow-ups owned by specialists deliver unchanged with real receipts; only authorized terminal reports/handbacks trigger relevant meta coordination. Progress remains an internal note.
3. **Production attempt runner.** Composition owns planner/runner/process lifetimes. Reuse worktree/model/env/isolation/journal/check helpers; adapter registry advertises proved capabilities only. Role-scoped MCP serves allowed reads/reports/permission bridges; workers cannot approve external effects or acquire meta authority. Redact before journal write. Journal replay dedupes `(attempt,generation,engineSeq)`; apply facts and state in a transaction, ack only after commit. Unsupported effects fail explicitly.
4. **Scheduler/integration controller.** Event-driven passes on authoritative reports, checks, capacity and relevant confirmations; atomically reserve actual capacity; enforce requested slot/model/tier/budget. Persist defer reason and release condition. Dependency/base policy gates dispatch. Run pinned repo checks on exact head, bounded repair/review/integration as required; a clean engine exit or empty accepted subset never means all work succeeded.
5. **Canonical observation/query boundary.** Typed list/work/task/attempt/decision/artifact DTOs shared by HTTP and bounded meta status tools; do not make engines import store. Derive stage/count/next action from the same facts using spec §10 order. Return timestamps/provenance/coverage; partial errors preserve stale data with a label. Redacted message/tool/report/artifact inspection is on demand, never hidden model reasoning.
6. **Bounded live observation.** Consistent snapshot plus cursor vector; one merged SSE connection with compact events/invalidations, per-stream last-applied cursor, duplicate handling, bounded catch-up and snapshot reset if history unavailable. Stream order is per stream; causal links supply relationships across streams. Keyset-paginated reads enforce row/byte limits, artifact path/root/type/size confinement and no executable markup. Heartbeat freshness/process identity differs from task activity and provider health.
7. **Outcome/accounting projection.** Incremental replayable derived view with version/watermarks. Requested vs actual model/effort, process vs validation vs delivery outcomes and usage source/time/mode are distinct. Mode-aware spend includes completeness; show known subtotal plus missing coverage, never estimate absent totals. Broader ranking/learning analytics and retention deletion are deferred.
8. **Frontend state/HTTP contracts.** Decode actual envelopes into view models, finite async states, pane error boundaries and request cancellation. Draft and explicit context are per repo, preserved across navigation/reload as a proposal. Freeze each submission's target/text/key; retry same payload/key, edited intent gets new key. Preserve text typed during pending send; prevent duplicate Enter dispatch.

Prefer additive JSON fields/versioned read DTOs first. Frozen `packages/contracts` additions require matching fixtures and `docs/handoff/CONTRACTS.md` §10. Do not silently change existing adapter meaning. Shared server routes follow append-only concern blocks. Narrowly extract admission/runner/controller/query helpers rather than grow `MetaAgentService` or composition into another monolith.

## Compatibility and safe defaults proposed for review

These are engineering recommendations, not extra owner-confirmed decisions: keep legacy records; only assign repo when evidence proves it; otherwise show Unassigned read-only and require explicit new admission for new work. Never guess association or reconstruct overwritten tasks. New IDs are global/transactional. No destructive auto-repair, retention deletion or stored-data migration is authorized.

Default to additive docs/read projections without SQL schema changes. A necessary numbered SQL migration is a separate approval checkpoint with backup, forward/backward compatibility/restore evidence and one blockers-only review; old binaries reject newer schema versions. A prior artifact alone is insufficient schema rollback. No credentials, raw private traces or personal identifiers in records; no secret bytes are needed for this work.

## Verification and acceptance gates

Builders add meaningful failing-before/passing-after regressions and targeted mutants for repo identity, duplicate/stale action, hold/stop/generation, redaction/artifact confinement and evidence-bound completion. Source inspection is not the failing run. Separate verifiers exercise the actual composed server/packaged entrypoint, not only mocked API screenshots. No agent reviews its own change. One blockers-only review applies to secrets/sign-in/permissions, money, stored-data deletion/migration, or public posts to another's repo; fixes need no re-review. Required human protections still apply.

Planned commands and fault cases are in [VERIFICATION.md](VERIFICATION.md): relevant Vitest lanes, `pnpm check`, web typecheck/screens, build/pack and wrapper verify. Accessibility/mutant runners must be concretely supplied rather than invented scripts. Real-engine canaries remain quota-gated and separately labelled. Screenshots are saved only after privacy sweep, in both themes; axe zero violations and Lighthouse accessibility ≥95 per route; visible focus, dialog return, meters, reduced motion and responsive evidence remain acceptance.

Final assembled outcome: owner selects repo, asks once, sees real versioned coordination, receives/answers an actual question if necessary, inspects truthful task/attempt/evidence, confirms named push and PR effects, receives a tested review-ready PR; decline/hold/stop/restart/offline cases preserve authority and work. Every new task retains repo/goal/origin and exact evidence. An unavailable engine/measurement fails honestly instead of fabricating success. No manual specialist dispatch is required.
