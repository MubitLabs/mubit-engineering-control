# Observability, repository identity and evidence — planning research

5 November 2026. Source checkout: `a102313`. Research only: no tests, engines, live state, credentials, external effects or product changes. Paths below are repository-relative. Source facts are high confidence unless explicitly labelled inference or proposal. The installed workbench may be a different build; source findings do not establish its current runtime behavior.

## Product outcome

The user speaks to the meta agent in a separate conversation/history for each repository (owner decision during this planning turn). Every new admitted coding request belongs to that registered repository and can be followed from its original message to plan, dependent tasks, delegated attempts, checks, decisions and delivery. The meta agent receives bounded summaries/report pages, not whole worker transcripts (§6). Reading a specialist's redacted activity is inspection for the user, not another chat the user must manage. The overview should answer what is happening, what is waiting, why, and what the user can do. Detailed evidence is available on demand without flooding the conversation.

The owner-selected default target is a tested PR ready for review; merge remains a separate decision. The meta agent may plan and execute authorized local work automatically, while push/PR/merge retain their explicit confirmation cards. Legacy history with an unknown repository remains unassigned and read-only; task collisions may already have destroyed association evidence and must never be guessed back into existence.

This mostly implements existing spec §§10, 12, 14, 17–20. Repository attachment needs an explicit identity contract; broadening “observability-lite” (§19) must stay bounded and local rather than introducing an unrelated telemetry platform.

## Proposed minimal architecture

Keep SQLite, the existing contracts seam, per-attempt journals and the single-writer core. Add focused boundaries rather than replacing them:

1. **Typed admission identity.** Stable repo/work/task/attempt IDs and validated ownership. Make dependency mapping and task persistence one atomic operation. Unknown legacy repo association remains unknown; do not guess based on a path/title.
2. **One durable fact path.** Runtime redacts before journal append; journal replay delivers facts idempotently by `(attemptId, generation, engineSeq)`. Core updates state and appends domain facts in the same transaction, then acknowledges the journal only after commit. Side effects stay behind their existing queue and confirmations.
3. **One canonical read model.** A small read-only query module joins repository/conversation/work/task/attempt/report/check/decision/artifact facts. It returns plain labels, reason, next action, observed timestamps, coverage and source references. Both UI and bounded meta-agent status tools read it; adapters never read the store directly. New work requires repo identity; tasks/attempts inherit the validated association rather than accepting conflicting client-supplied repo IDs.
4. **Incremental projections.** Persist a version and per-stream cursor/watermark for derived outcomes/timeline summaries; rebuilding from facts is deterministic and idempotent. Avoid a global wall-clock ordering claim: streams have gap-free sequence within a stream, not across all streams. Cross-stream ordering uses explicit causation/links and an approximate display time with a stable tie-break.
5. **Bounded observations.** Initial repo/work/task snapshot carries a cursor vector captured consistently; one merged SSE stream sends invalidations or compact fact envelopes. Reconnect uses the last applied cursor per stream; duplicates are ignored, gaps trigger bounded catch-up, and an unavailable history segment triggers a fresh snapshot with an honest notice. Paginated redacted transcript/tool/artifact reads load only when the user opens them. No unbounded raw-event payload in the overview.
6. **Independent liveness.** Server connection and heartbeat, queue progress, last agent activity and task wait reason are different signals. Show stale evidence explicitly and retain it while reconnecting. “No activity for …” should not automatically mark a model task failed; use deterministic process/session evidence before replacement.

Suggested modules are new focused read-model/query/projection modules in the owning packages and an API DTO module at the existing seam. Keep existing server route conventions. Use additive optional contract fields or a new versioned read DTO, update matching fixtures and CONTRACTS §10. Read-only projections can initially use current JSON docs; add measured generated-column indexes or dedicated projection tables through numbered immutable migrations only when necessary. Schema rollback is not covered by a feature flag: old binaries reject newer migrations (`store/migrations.ts:46–56`), so migration rollout needs a compatible prior artifact or an approved restore plan.

## Full observability, privacy and honest limits

Default view: repo, request title, intended outcome, current phase, task counts, dependency blockers, last activity, “needs you” and next action. One selection reveals task objective, role/parent, slot/provider, requested tier and actual model, attempt history, checks on exact SHA, review findings and disposition, artifact links, handoffs and delivery receipts. Timeline explains decisions and transitions; transcript inspection shows only redacted messages and tool inputs/outputs.

Do not promise private chain-of-thought visibility. The product can expose plans, stated decision reasons, actions, tool results, reports, errors, costs and provenance, not hidden model reasoning. Local trace storage still may contain source code or user text. Redaction is before every durable write, not only before serving HTTP. The generic `DocsRepository.save` and event log serialize without their own filter (`store.ts:135–138,181–188`), so the production composition must prove every ingress is redacted; this is a wiring requirement, not proof that all current paths leak.

Keep credentials, identity metadata not needed for the journey, and arbitrary paths out of routine summaries. Read artifact files only through an allowlisted local root/reference resolver with size/page limits; render code/output as text. Retained decisions should preserve metadata and hashes even if an expired bulky log becomes unavailable. Export should be an explicit user action with a redaction preview, not automatic telemetry.

## Decisions for the owner

1. **Confirmed product choice:** Separate meta conversation/history per registered repo. **Proposed safeguards:** new admitted work requires repo identity; task/attempt associations inherit it. Unknown legacy history remains unassigned/read-only and overwritten records are not reconstructed by inference.
2. **Confirmed:** Tested PR ready for review is the default completion target, merge separate. Autonomous local planning/execution does not waive push/PR/merge confirmation.
3. **Recommended within that direction:** Compact status/timeline by default with full redacted tool/transcript/artifact inspection on demand; bounded summaries/report pages go to the meta agent. No private chain-of-thought exposure.
4. **Later decision, not a blocker:** Keep intended retention periods without enabling deletion in this pass. Source-containing transcript retention execution and export need a separate owner-approved plan; neither is required for initial observability.
5. **Recommended metric semantics:** PR-ready/delivery success comes from actual acceptance evidence and confirmed output, with process completion separate. Correct current labels now; broader historical comparisons/ranking are deferred.

## What was ruled out

No new hosted telemetry stack, graph database, store rewrite or broad ORM migration is necessary for the stated journey. Existing per-stream sequences, transactions, engine envelopes, unknown-handling and journal helpers provide a useful base. The problem is missing durable identity/joins/composition and incomplete evidence exposure, not absence of every building block. No provider account introspection or credential bytes are needed for this plan.
