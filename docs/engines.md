
## OpenCode 2.2.5 canary learnings (real serve API, 3 Nov 2026 — R2.2)

Recorded against slot glm-2 (z.ai GLM Coding Plan, key verified live against `https://api.z.ai/api/coding/paas/v4/models`, Bearer) and slot gem-1 (Google Gemini, `generativelanguage.googleapis.com/v1beta/models`, x-goog-api-key). Fixtures `smoke` (real, the adapter-driven OPENCODE-H1-OK turn) and `auth_expired` (real, garbage-key 401) are recordings; `rate_limit_rejected` and `permission_request` are synthetic in the real envelope (quota / spec-derived; see each meta.json).

**How opencode consumes keys (the launch recipe).** No `opencode auth login` needed — config-file providers carry API keys: an `opencode.json` in `$XDG_CONFIG_HOME/opencode/` (or `OPENCODE_CONFIG_DIR`) with `provider.<id>.options.apiKey: "{env:VAR}"` — `{env:}` substitution is resolved at launch, so the key rides the environment (keystore read → launch env) and NEVER enters a file opencode persists (verified: `debug config` prints `apiKey: "***"`). GLM: `npm: "@ai-sdk/openai-compatible"`, `baseURL: https://api.z.ai/api/coding/paas/v4` (the endpoint that bills Coding Plan quota), model `glm-4.7` (catalog: glm-4.5…glm-5.3-flashx-legal). Gemini: `npm: "@ai-sdk/google"`, model `gemini-2.5-flash` — same flow, verified with a real turn. `opencode auth list` lists only integration (OAuth) logins — a working key slot shows `[]`; the honest validity probe is the zero-token provider /models GET (slots probes, R2.6).

- **Isolation**: XDG_{DATA,CONFIG,STATE,CACHE}_HOME → the slot home; `OPENCODE_DISABLE_PROJECT_CONFIG=1`. CLI subcommands default to a SHARED background service on a fixed port (cross-slot hazard; one was already running) — always `--standalone` for CLI, `serve` per slot for the API.
- **`opencode serve --hostname 127.0.0.1 --port 0 --stdio`** prints exactly one stdout line `{"url":"http://127.0.0.1:<port>"}`; connect over HTTP with Basic auth user `opencode`, password from `OPENCODE_PASSWORD` (401 without, 200 with). **stdin EOF shuts the server down** (spawn with stdin piped open, never ignored). The full API surface + schemas: `GET /openapi.json` on the live server (zero-token ground truth, like codex `generate-ts`).
- **`POST /api/session`** takes `{location: {directory}, agent, model: {id, providerID}, permissions}`; the response is ENVELOPED `{data: {id}}`; the location directory MUST exist on disk (`LocationNotFoundError` otherwise); `session.create` without a model does NOT inherit the config-file default (pass `{id, providerID}` — the runtime owns the slot's provider profile, plan §5.7). Real agent ids: `build` (default), `plan` (read-only) — not `read-only`. `POST …/prompt {text}` always 200s (enqueue); failures arrive as events.
- **The real SSE stream** (`GET /api/event`): single `data: {"id","created","type","location","data":{…}}` lines — name top-level, payload nested under `data`; `: heartbeat` comments; no `event:` name lines. NO `session.idle`: the turn end is `session.execution.succeeded` / `.failed` — and the server keeps talking AFTER the verdict (a final cumulative `session.usage.updated`, `session.renamed`), so the adapter HOLDS the exit and flushes it at stream end (CONTRACTS §1 exit-last). Usage shape: `tokens: {input, output, reasoning, cache: {read, write}}` (not flat cache_read/write); the GLM Coding Plan reports `cost: 0` (subscription-style, never a number to charge); `session.usage.updated` fires more than once per turn, cumulative. Assistant text: `session.text.ended {text}`. Tools: `session.tool.input.started {id, name}` → `session.tool.called {id, input}` → `session.tool.success/failed {id, content, metadata.exit}` → one `tool_call`.
- **Errors** arrive as `session.step.failed` + `session.execution.failed` with `data.error = {type: "provider.auth", status: 401, message, response: {body: "<provider JSON string>"}}` — dot-namespaced types, the provider body stringified one level down (z.ai: `{"error":{"code":"1000","message":"身份验证失败。"}}`). Classification reads `type`/`status` plus the parsed body.
- **Permissions**: the runtime request is `Permission.Request {id: "per_…", action: "shell", resources: ["touch x"], save: ["touch *"], source: {type: "tool", id}}` — action `shell`, NOT `bash` (the config key is `bash`; the default `build` agent's ruleset starts `{action:"*",resource:"*",effect:"allow"}`, which swallows any appended ask — set `agent.build.permission.bash: "ask"` in the slot config to REPLACE it; a `permissions` ruleset on session.create alone does NOT ask). Reply: `POST /api/session/:id/permission/:perId/reply {decision: "once"|"always"|"reject"}` → **204 with an EMPTY body**; there is NO echo event — the adapter synthesises `permission_result`. **A reply POSTed from outside the SSE read loop (a `reader.read()` pending in flight) stalls the turn forever** — 204 lands, the pending list clears, execution never resumes; the identical reply between reads works, even 3 s late. The adapter therefore runs the whole round trip (bridge → reply → synthesised result) inside its SSE pump, between reads. Reproducible on both the free tier and glm-4.7.
- **Free tier**: opencode's built-in `opencode/glm-5.3-flash-free` models burn no Coding Plan quota — the permission-mechanism debugging ran there.

## Codex 0.148.0 canary learnings (real app-server, 3 Nov 2026)

Recorded against the logged-in `codex-1` slot (`CODEX_HOME=~/.mec/engines/codex/codex-1`, "Logged in using ChatGPT"); protocol cross-checked with `codex app-server generate-ts` (ships with the binary — the cheapest source of truth, zero quota). Fixtures: `smoke`, `permission_request`, `auth_expired` are real recordings; `rate_limit_rejected` stays synthetic.

- **Handshake**: `initialize {clientInfo:{name,title,version}, capabilities:{experimentalApi,requestAttestation}}` → `{userAgent, codexHome, platformFamily, platformOs}`; then the client NOTIFICATION `initialized` (no id) before anything else. `thread/start {cwd, sandbox, approvalPolicy}` → `{thread:{id,…}, model, …}`.
- **The plan's 0.166 description is wrong for turns on 0.148.0**: `turn/start` takes `{threadId, input:[{type:'text', text, text_elements:[]}]}` — not `{prompt}`; `turn/steer` needs `{threadId, input, expectedTurnId}` and `turn/interrupt` needs `{threadId, turnId}`. The turn id exists only in the `turn/started` notification (`params.turn.id`), so a steer/interrupt before events are drained is impossible — the adapter refuses with a clear error.
- **Approvals are server→client REQUESTS, not notifications**: the request id rides at the TOP level (`params.id` does not exist; the observed id was the number `0`). `item/commandExecution/requestApproval` params: `{threadId, turnId, itemId, startedAtMs, environmentId, reason, command, cwd, commandActions, proposedExecpolicyAmendment, availableDecisions}` — `command` is ONE shell-line string (`"/bin/zsh -lc 'touch approved.txt'"`), not argv. The answer is the JSON-RPC response `{"jsonrpc":"2.0","id":<same id and type>,"result":{"decision":"accept"}}`; `item/tool/requestUserInput` is answered `{"answers":{}}` — it has no decision vocabulary.
- **A read-only sandbox + `approvalPolicy: on-request` escalates writes** (the observed `touch`), while plain reads (`ls`) run in-sandbox without asking. `fileChange` approvals carry no paths — only `reason` and an optional `grantRoot`.
- **`turn/completed`** carries the whole turn: `params.turn.status` ∈ completed|interrupted|failed (+ `turn.error` when failed) — not a flat `status`.
- **`thread/tokenUsage/updated`** nests cumulative tokens under `params.tokenUsage.total` (`inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`); ChatGPT subscriptions report NO cost — `cost_usd` stays undefined, never 0.
- **`account/rateLimits/updated`** carries `params.rateLimits.{primary,secondary}` (300/10080 `windowDurationMins`; `resetsAt` unix seconds) — one event per window. Live slot readings at canary time: five_hour 0–1%, seven_day 16%, `planType: "team"`, credits enabled.
- **Auth expiry (empty CODEX_HOME) never ends the turn**: 401s arrive as `error` notifications `{error:{message:"Reconnecting… N/5", codexErrorInfo:{responseStreamDisconnected:{httpStatusCode:401}}, additionalDetails:"unexpected status 401 Unauthorized …"}, willRetry:true}` — the message alone says nothing about auth, classification must read `codexErrorInfo`/`additionalDetails` (401/unauthorized → auth). No `turn/completed` ever comes; the server retries forever, so the runtime must kill it and the exit is the CONTRACTS §1 crash-rule synthesis.
- **`mcpServer/startupStatus/updated` carries `error: null` in flight** — parsers must not mistake a null error field for an error notification.
- **The app-server never exits on its own** after a turn; consumers must stop draining at the `exit` event (or kill the process). Model on the slot: `gpt-5.6-sol`; `thread.cliVersion` is a reliable per-thread engine version.

## H1 canary learnings (Claude Code 2.1.317, 3 Nov 2026)

- `--session-id` requires a UUID (attempt ids like `att_1` are rejected with "Invalid session ID").
- `-p` with `--input-format stream-json` waits on a stdin user message; one-shot launches must not pass it.
- `--settings /dev/null` errors — always point at a real file.
- MCP: the client performs the full handshake; a server that cannot answer `initialize` is dropped ("Available MCP tools: none"). The `mcpServers.<name>` entry `{type:'http', url, headers:{Authorization}}` works on 2.1.317; the server URL includes the `/mcp` path.
- Sandboxed writes INSIDE `sandbox.filesystem.allowWrite` do not trigger `--permission-prompt-tool`; Bash commands do. The permission-prompt tool response shape is `{behavior:'allow', updatedInput}`.
- Slot utilisation at canary time: five_hour 4%, seven_day 10% (live readings in the stream).

## H3 sandbox learnings (GitHub, 3 Nov 2026)

- `gh repo view` takes the repository as a POSITIONAL argument; `-R` is only for pr/issue commands.
- `gh pr checks --json` reports states UPPERCASE (SUCCESS/PENDING/FAILURE).
- `gh pr create --body-file -` reads the body from stdin — a runner that does not close stdin hangs until timeout.
- Branch protection: the required context must equal the check-run name EXACTLY (this workflow reports `check`; requiring `ci / check` silently blocks every merge with "base branch policy prohibits the merge"). `gh pr view --json mergeStateStatus` is the ground truth (CLEAN vs BLOCKED).
