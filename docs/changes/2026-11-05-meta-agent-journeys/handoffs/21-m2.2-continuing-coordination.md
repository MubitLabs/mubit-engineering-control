## Outcome

A multi-task plan runs to its end without another user message. Each next wave dispatches when dependencies and capacity allow, on a slot and model that satisfy the request. A failed prerequisite blocks its dependents with a reason. A follow-up on running work reaches the owning specialist unchanged, with a truthful receipt. Reports wake the meta agent only when §6 says so.

## Requirements

1. **Scheduler pass (§11).** `10` extracts the dispatch block of `#commitPlan` into a private method used by lift. Move that method into `packages/meta/src/scheduler.ts`. One function, inside `atomic`, used by plan commit, lift and passes. Run a pass after effects on the 2s timer and on command: report, check result, lift, resume, slot change. Passes never run while paused.
2. **Task states are real.** Today every dependency reads as `ready` because the map is built from the new plan. Read persisted task state.
3. **`queued` occupies capacity.** `ACTIVE_ATTEMPT_STATES` omits `queued` (`states.ts:202`), so a second pass 2s later sees neither the task nor the slot as taken and launches again. `planDispatches` rule 1 keys on that list. §11's "unique index" doesn't exist: `migrations.ts` has one `docs` table with a text key. Enforce one live attempt per task inside the `atomic` that reserves, counting `queued`. A `queued` attempt whose launch row ended `failed` is the interim state from `20` open question 2: it must not hold capacity. No migration.
4. **Base policy.** Persist `basePolicy` on the task. Add optional `base_policy` to `propose_plan` (`mec-tools/src/tools.ts`, parser `meta/src/tools.ts`), default `integration`. Remove the hardcoded value at `service.ts:570`, `tools.ts:396`, `real-brain.ts:536`.
5. **Interim acceptance.** `dependencySatisfied` needs `accepted` or `integrated`, and nothing produces either before 22. The plan's M2.2 acceptance ("two dependent tasks finish") can't otherwise hold. Add one rule: an attempt that `succeeded` with no review required moves the task `work_complete` then `review_accepted`, through `TASK_MACHINE`. Put it in one function that 22 replaces. Prove the end-to-end chain with `contract` dependents, which start from the pinned base. `integration` dependents are proven with real integration in 22, and with injected `integrated` state in unit tests here.
6. **Placement (§11, O7).** Candidates come from authoritative slot state: engine in the runner registry, explicit `slotHint.slotId` honoured, model or tier resolvable on that slot via `resolveModel`, real `inUse` from attempts. Replace `inUse: 0, concurrency: 1` (`service.ts:732`). Add `slotClass` and utilisation to `slotViewsFromStore`. Extend `SchedulableTask` and `planDispatches` in `packages/domain/src/scheduling.ts`. Unavailable never silently becomes a default (`resolveModel` header). Record rationale, resolved model and effort, and any `tier_degraded`, on the attempt before launch.
7. **Defer reasons.** Persist `deferred` on the task: reason and what releases it. `planDispatches` computes them and `#commitPlan` drops them today.
8. **Hold and stop (#20, §13.4).** `10` fences the plan commit and lift. Passes need the same rule: nothing launches for held, stopped or withdrawn work. Lift triggers a pass.
9. **Plan revisions (#19, §10).** Immutable `plan/<wi>/<n>`, using M1.2's actual shape. Within a work item a reused key is the same task: same canonical id, history, attempts, status; never reset. A new key is a new task. Store the impact summary from `domain/impact.ts`.
10. **Reports to wakes (§6).** `classifyWake` has no production caller. Route reports through it: `ready`, `blocked`, `failed`, `dropped` and questions call `enqueueWake` from `11`, in the same transaction as the report. `progress` and `waiting` become notes. `11` makes the `note` and `deliver` handlers throw `unsupported effect`; replace both. Store notes for the next turn's context.
11. **Failed prerequisite.** A task with no attempts left blocks with a reason, and so do its dependents. Bounded repair is 22.
12. **Follow-ups (§12.3, §12.4).** `#noteAttached` and `#noteConversation` persist an ack and deliver nothing. Find the attempt that owns the reference. Enqueue `deliver`, key `deliver:<attemptId>:<inputId>`, payload the contract `Input` with text unchanged. The handler calls `Runtime.deliver`.
    - While owned, the meta agent may only stop: no replan, answer or reroute.
    - `handback` uses `handBack()`: once, with a reason, routed never to the same attempt.
    - Unhandled messages at work end are released as fresh candidates.
    - `routeMessage` needs live `openQuestions` (`service.ts:252` hardcodes `[]`).
13. **Receipts.** Persist the stage on the message doc. `ReceiptLadder` is in-memory: hydrate per message, write through. `delivered` when the engine took it; `read` only after a turn end or report; `handled` from `handled_inputs` or handback; `settled` on the result or reroute.
14. **Make Claude `send` real.** It only pushes to an array (`adapter.ts`), stdin is `ignore`, and `argv.ts` deliberately omits `--input-format stream-json`. §9 names that flag. Wire it, including when stdin closes so the process still exits. A successful write isn't `delivered` unless the engine took it (§12.4). The one real run belongs to the verifier, who sweeps the recording and hands it to you to commit as a fixture, `recorded_by: 'real'`. If it can't be made safe at 2.1.317, see the open question.
15. **Unsupported engines.** An engine with no proven `send` gets `deliveryFailed`, and the message is released to the meta agent with the reason. Never a fake receipt.
16. **Questions (§10, §12.6).** Specialist `ask_user` and `report.question` create one `question/<id>` card with the original text and evidence. Same text reuses, different replaces, `ready` closes. The answer goes to the asking attempt through `deliver`, not through a planner replan. `11` moves the answer into the service with a wake: branch there on who asked, and keep the wake for planner questions.
17. **Cards from specialists.** `request_confirmation` opens a card, and the `confirm` decider may wait on one for confirm-by-default classes (§13, `BridgeImpl` deadline). Always-confirm classes stay denied. A specialist never resolves a card.
18. **Reserved wake capacity (§11, §26).** With all slots busy, a follow-up delivery goes before any queued launch.

No contracts change expected: `base_policy` is a tool schema field. If `Input` or `Report` needs a change, stop.

## Open questions

1. **§9 and §12.3: mid-turn input on Claude 2.1.317.** The spec names `--input-format stream-json`, the code avoids it, and no recording exists. Open because exit behaviour under an open stdin is unobserved. Recommend stream-json. Fallback: deliver at turn end through `--resume` in the same slot, with `delivered` only then. That loses steering mid-turn and needs the owner's agreement.
2. **§10 and #19: a replan that drops a key.** #19 covers reuse, not removal. Recommend: not started → `cancelled` with the revision as reason; started → kept, flagged in the impact summary, for the meta agent to stop explicitly.
3. **§15: acceptance with no reviewer.** §10 says review makes a task `accepted`, and a `ready` report means reviewed work. #13 says routine work needs no independent review. Recommend passing checks on the exact head as acceptance for routine tasks, and 22 replacing the rule. This is an interim reading until the owner confirms it.
4. **§12.6: does an answered specialist question also wake the planner?** Recommend no: deliver to the specialist, note to the meta agent.
5. **`VERIFICATION.md` "stale plan" (Human actions row).** The spec defines stale for confirmations (§10, input changed) but not for a question asked under a plan revision that a replan has replaced. Recommend keeping the question's work id, recording its revision on the doc, and showing the planner that revision with the answer.
