# M8 — Planning and the coordinator

**Backlog tickets:** 14 (plan revisions, requirements, task-graph validation), 15 (coordinator
tools and task proposal review).

## What it does

- **Two paths to a task graph.** A delivery's plan revision can be written by hand (requirements and
  tasks as JSON on the delivery page — deterministic, used in tests), or proposed by a
  **coordinator**: a normal coding agent in *Observe* mode (read-only tools, `dontAsk`) on the
  pinned base, started from the delivery page with one of your execution profiles.
- **The coordinator's only write is `propose_tasks`** (an MCP tool exposed only to coordinator
  attempts). Control parses the proposal against the task specification (PDF §8), runs the M1
  graph validation with the repository's check names and available profiles, and either returns
  the exact errors for repair or submits the revision for the delivery owner's approval. After four
  invalid proposals the plan becomes a human decision. The coordinator cannot approve, widen
  budgets or grant accounts — approval stays with the delivery owner and the plan approval card.
- **The coordinator is an ordinary attempt** of a hidden per-delivery *planning* task (`mec-plan-n`,
  a reserved prefix humans and agents cannot use), so it reuses claims, leases, journals,
  interrupt/resume and the decision bridge (it can ask questions). Planning tasks never reach the
  scheduler, the readiness rules or integration.
- **Plan revision view.** The delivery page shows the task graph (dagre layout of the stored graph;
  live task states once approved, warnings highlighted before), requirements traceability (which
  tasks cover each requirement; uncovered ones flagged), validation errors and warnings, and the
  revision history.
- **Revising an approved plan.** Approved revisions are immutable; an edit opens a new revision.
  On submission its **impact summary** lists added, changed (with work that would stop), removed and
  unchanged tasks. On approval, unchanged tasks **carry over with their state and work**; changed or
  removed unfinished tasks are cancelled (a running attempt is asked to stop); integrated work stays
  in the integration branch.

## How to demo

`pnpm vitest run apps/control/test/planning.test.ts` — a coordinator proposes a cyclic graph, gets
the cycle back, proposes a valid three-task graph, which a member cannot approve and the owner
does; tasks without prerequisites become ready. Repeated invalid proposals stop at the bound. A
non-coordinator cannot propose. Revising an approved plan keeps an in-review task and replaces only
the changed one.

Live: create a delivery with a plan on the sandbox repository, choose a Claude Code profile in the
Coordinator panel and run it; approve the proposed revision in the decision inbox.
