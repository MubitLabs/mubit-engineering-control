# M7 — Claude Code adapter and decision inbox

**Backlog tickets:** 05 (CLI probe, capability registry), 06 (Claude adapter, decision bridge),
09 (owned execution profiles and delegation grants), 12 (live workbench), 13 (decision inbox,
atomic answers, stale-request handling).

## What it does

- **Capability probe.** For the installed Claude Code (2.1.292 on the droplet) the runner checks
  the version, native sign-in (`claude auth status`), and that every flag the adapter relies on is
  accepted (`-p`, `stream-json` in and out, `--mcp-config`, `--strict-mcp-config`,
  `--permission-prompt-tool` — present but undocumented in this version — `--permission-mode`,
  `--allowedTools/--disallowedTools`, `--session-id`, `--resume`, `--replay-user-messages`,
  `--restricted`). None of this sends a prompt. Unproven flags are reported as unsupported; the
  result is the profile's capability set (`structured_stream`, `questions`, `tool_approval`,
  `interrupt`, `native_resume`, `usage`). Probes repeat every five minutes over the heartbeat so an
  expired login shows up as `auth_required`.
- **The adapter.** Claude runs headless (`-p`, stream-json both ways) in the attempt's worktree with
  `--restricted` (file tools confined to the working directory) and a per-attempt `mec` MCP server
  (`--strict-mcp-config`, so no other MCP servers load). Execution modes map to what Claude actually
  enforces:
  - *Observe* (coordinator): `dontAsk`, read tools only.
  - *Implement*: `acceptEdits`; the task's acceptance commands and read-only git are pre-approved;
    every other command goes to the inbox.
  - *Assisted*: `manual`; edits and commands all go to the inbox.
  Owned paths remain instructions, not a sandbox (PDF §13).
- **Decision bridge.** The `mec` MCP server (`apps/runner/src/mcp/server.ts`) exposes `approve`
  (the permission prompt tool), `ask_question` and `report_result` and forwards calls over a
  private Unix socket to the runner. The runner journals `attempt.input_requested`; control turns it
  into one durable approval bound to the exact attempt generation and input. Tool use is decided by
  the **account owner** (and delegates); questions by the delivery and task owners. The first
  authorised answer wins (M2's compare-and-set) and travels back as a `resolve_decision` command.
  Expired requests are answered `closed` and the agent is told it was **not** approved; interrupting
  or resuming makes open requests stale, so a late click authorises nothing.
- **Stream normalisation and usage.** stream-json is normalised once into `agent.message`,
  `agent.tool_use` / `agent.tool_result` (with native ids), `agent.usage` (reported tokens and cost
  when present, `null` otherwise — never zero) and `agent.turn_result`. Thinking blocks are not
  recorded. Credentials are redacted before anything is journalled.
- **Quota and sign-in failures** park the attempt (`quota_wait`, `auth_required`) with the workspace
  preserved and a visible task blocker; there is no automatic account switching.
- **Execution profiles** (`Accounts` page). Only a runner's owner can offer its native agent
  account, choose the projects it may work on and the colleagues who may use it, and revoke it.
  Admins do not inherit this. The scheduler only assigns a profile the task owner may use.
- **Steering messages** form one ordered queue per attempt; a retried send with the same client key
  is not injected twice; the runner confirms delivery.

## How to read it

| Path | Purpose |
| --- | --- |
| `packages/agents/src/claude/adapter.ts` | argv per mode, MCP config, turn handling, interrupt/resume, failure mapping |
| `packages/agents/src/claude/probe.ts` | Version, auth and flag verification |
| `packages/agents/src/claude/stream.ts` | stream-json → events, failure classification |
| `packages/agents/src/claude/bridge.ts` | Unix-socket bridge between the MCP server and the runner |
| `apps/runner/src/mcp/server.ts` | The `mec` MCP server Claude launches |
| `apps/runner/src/runner.ts` (`requestDecision`) | Journals requests, waits for the answer |
| `apps/control/src/features/decisions/service.ts` | Approval creation, binding, answer and expiry |
| `apps/control/src/features/profiles/routes.ts` | Profiles and grants |
| `packages/testkit/fixtures/fake-claude.mjs` | Stand-in CLI that speaks the same flags, stream-json and MCP |

## How to demo

Tests: `pnpm vitest run packages/agents apps/runner/test/mcp-bridge.test.ts apps/control/test/claude-e2e.test.ts`
— approval for the account owner (a viewer and a member get 403), approve and reject reaching the
agent, a question answered by the delivery owner, expiry answered as closed, interrupt making a
pending request stale, a usage limit parking in `quota_wait`, an idempotent steering message, and
delegation grants.

Live on the droplet (needs Claude Code signed in as `max`: `ssh droplet-max`, `claude`, `/login`):
create a profile on the Accounts page for `droplet-max / claude-code`, grant it the project, start an
attempt on a task with that profile, approve the command card that appears in the inbox.
