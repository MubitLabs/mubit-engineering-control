# M3.3: Complete setup and configuration

Read `00-README.md` first. This handoff is two PRs. Stage B is a small follow-up that waits for M2.4.

**Branch:** `feat/setup-config`. Stage B `feat/recovery-controls`.
**Size:** L. Stage B S.
**Model:** the strongest available. This touches keys, trust, policy and irreversible controls.
**Start when:** `fix/release-cards`, `fix/http-recovery`, `feat/visual-foundation`, `feat/repo-identity`, `feat/repo-workspace`, `feat/authority-fence` and `feat/durable-commands` are on `origin/main`. M2.4 is not required: Switch work and Drain stay honestly unavailable until Stage B. Stage B: `feat/setup-config`, `feat/work-live` and `feat/m2.4-recovery` are on `origin/main`.
**Can run alongside:** `30-m3.1-canonical-inspection.md` both stages, `31-m3.2-observable-work-ui.md` all stages, `33-m3.4-accessibility-local-release.md` Stage A, and all of M2. Stage B the same, with nothing left of M2 to wait for.
**Blockers-only review:** required, by a different agent. Sensitive controls: key replacement, slot retire, repository trust, policy apply, meta-slot choice, and the backup archive's contents. Stage B: not required; it only calls the route `23` built and reviewed.
**Real-engine runs:** none. Engine detection uses zero-token local probes only.

**Credentials:** no agent ever enters, reads or generates a real credential, in a test, a form or a verification. Keys enter only through the Connections form and `SlotKeystore`. Automated tests use the existing seams (`validateFetch`, `probeCmd`, `keystoreRoot`) with obviously synthetic values. **The owner enters real credentials.**

## Outcome

On the next shell the owner can set MEC up from nothing, or return to a partial setup, and can tell what is really ready. They can add a second repository without repeating the wizard. They can add, replace and retire connections, and every irreversible step says what it does. They can edit policy, prompts, models and repositories durably. A stale save keeps their draft. No control pretends to work.

## Open questions

1. **§13, retire.** "Deleting a slot or its keystore" is always-confirm, which reads as a confirmation card. CHANGE.md describes an arm-and-confirm control. Recommendation: inline two-step plus the server label guard, because a retire has no remote effect to journal. A card is the alternative if the owner wants the audit record.
2. **§13, §18, when a policy edit takes effect.** The spec doesn't say. Policy is read at construction, and M1.2 pins `policyHash` at admission. Recommendation: new admissions only, needing a restart if it can't be done without `service.ts`, with the UI saying which.
3. **§14, removing a repository.** No route exists and §18 doesn't ask for one. Recommendation: not in this PR.
4. **§5.5, §18.4, Drain and pairs.** Listed as actions, not served. Recommendation: show as unavailable until M2.4 or later.
5. **§22, trust.** Should flipping trust on need a card rather than a two-step? Recommendation: two-step here, with the event recording it.
