# M2 — Control API, identity, events and web shell

**Backlog tickets:** 02 (login, membership, authorisation), 13 (atomic answers), 14 (plan revisions API).

## What it does

- **Identity.** GitHub OAuth restricted to *active* members of `GITHUB_ORG` (MubitLabs). The GitHub
  token is used once to check membership and is never stored. Sessions are Postgres rows keyed by
  the SHA-256 of a random cookie token (`httpOnly`, `SameSite=Lax`, `Secure` behind https).
  Admins come only from `MEC_ADMIN_LOGINS`. `AUTH_MODE=dev` adds a password-less login for local
  work and tests; the config refuses it unless both `HOST` and `PUBLIC_URL` are loopback.
- **Projects, members, repositories.** Admins create projects; project owners add members by
  GitHub login and register repositories with a validation profile (named argv commands, no shell
  strings). Clone URLs must be plain `https://` without credentials.
- **Deliveries and plan revisions.** `POST /api/deliveries` is idempotent on `idempotencyKey`.
  Revisions are edited with `expectedVersion`; a stale version gets `409 version_conflict` with the
  newer text. Submitting runs the M1 graph validation (422 with the issues if invalid) and opens a
  plan approval bound to the revision's content hash. Approval makes the revision immutable,
  supersedes the previous one and materialises tasks; tasks without prerequisites become `ready`,
  others record a `dependency` blocker.
- **Approvals.** `POST /api/approvals/:id/resolve` locks the row, checks it with
  `checkResolution` (pending, not expired, listed decider, binding unchanged) and updates it. Two
  concurrent answers: one wins, the other gets `409 already_resolved` with the recorded result.
  Expired → `410` and the request is closed as `expired`; changed input → closed as `stale`.
- **Events.** Every state change writes an event in the same transaction (`features/state.ts`).
  `GET /api/projects/:id/events` is SSE whose `id` is the stream sequence, so the browser's
  automatic `Last-Event-ID` reconnect resumes exactly where it left off.
- **Web shell.** Login, projects, project overview (deliveries, repositories, members, live event
  feed), delivery page (plan editor with conflict handling, submit/approve, tasks with blockers,
  decisions) and the decision inbox.

## How to read it

| Path | Purpose |
| --- | --- |
| `apps/control/migrations/0002_core.sql` | Users, sessions, projects, repositories, deliveries, plan revisions, tasks, approvals, audit log |
| `apps/control/src/app.ts` | Wires features into Fastify; serves the web build with SPA fallback |
| `apps/control/src/features/state.ts` | The single write path for state: machine check + compare-and-set + event |
| `apps/control/src/features/approvals/service.ts` | Approval creation, atomic resolve, per-kind hooks |
| `apps/control/src/features/plans/service.ts` | Revisions, optimistic edits, submit, plan approval hook, task materialisation |
| `apps/control/src/features/events/routes.ts` | SSE with resume cursor |
| `apps/control/src/features/auth/` | OAuth flow, sessions, dev login |
| `apps/web/src/features/` | One folder per screen |

## How to demo

```bash
pnpm db:up && pnpm build
DATABASE_URL=postgres://mec:mec@127.0.0.1:5434/mec AUTH_MODE=dev MEC_ADMIN_LOGINS=admin \
  node apps/control/dist/main.js
# open http://127.0.0.1:4100, sign in as "admin"
```

Integration tests (`apps/control/test/`): auth gating, OAuth org check and state validation,
cross-origin refusal, idempotent delivery, version conflicts, graph rejection, the approval CAS
race, admin-is-not-a-decider, stale and expired approvals, SSE history + live + resume.
